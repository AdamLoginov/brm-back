ХРАНЕНИЕ ФАЙЛОВ — ПЕРВЫЙ ЭТАП

1. Новые загрузки
По умолчанию корень — uploads относительно рабочей директории backend.
Можно задать абсолютный UPLOAD_ROOT. На сервере: /var/lib/brm/uploads.

Пример:
uploads/employees/187_Иванов Иван Иванович/Документы/Паспорт/34_Паспорт.pdf
uploads/employees/187_Иванов Иван Иванович/Фото/35_Фото.jpg
uploads/mail/incoming/2026/11/42_Документ.pdf
uploads/mail/outgoing/2026/11/43_Документ.pdf
uploads/mail/legacy/2026/11/12_Документ.pdf
uploads/company/company_card.pdf
uploads/tmp/ (временные загрузки)

ID различает однофамильцев и одноимённые документы. ФИО и название файла
остаются читаемыми. Недопустимые символы заменяются, расширение остаётся в конце.
Фото определяется категорией «Фото», остальные категории — внутри «Документы».

StoredFile хранит относительный ключ, исходное имя, размер, MIME, SHA-256,
тип и ID загрузившего пользователя (0 для старых файлов и входящей почты).
EmployeeDocuments/Attachment ссылаются на StoredFile. Старые поля сохранены
для совместимости. Старые файлы работают без обязательного переноса.
URL просмотра/скачивания и проверка авторизации остаются прежними.
Uploads нельзя публиковать как статическую папку в веб-сервере.

Лимит одного нового файла — 64 МиБ; пустые файлы не принимаются.
Файл записывается во временный каталог, проверяется и публикуется без
перезаписи существующего. При обычной ошибке транзакции новая копия удаляется.
При аварийном завершении процесса могут остаться неиспользуемые копии/tmp;
автоматической очистки в этом этапе нет. Удаление документа остаётся мягким.
При изменении ФИО перенесённые файлы копируются в папку нового ФИО, ссылки
обновляются в транзакции. Старые копии сохраняются, чтобы не терять данные.
Изменение категорий прямым SQL не синхронизирует папки автоматически.

2. Перенос существующих файлов
Сначала остановить backend. Команда не должна работать одновременно с
загрузкой файлов или изменениями карточек. Корень должен быть доступен на запись
пользователю backend; файловая система должна поддерживать hard links (NTFS/ext4).
Предварительный просмотр читает SQLite в режиме ro, не меняет БД/файлы,
записывает только JSON-отчёт. Не запускать от root без исправления владельца
созданных файлов: на сервере команда должна выполняться от пользователя brm.

Из каталога project локально:
go run ./cmd/migrate-files -db test.db -root uploads -report ../file-migration-preview.json

Проверить отчёт: ready — доступен; missing — отсутствует; error — ошибка.
Для каждой записи указаны источник и новое расположение. Файлы вне uploads
не переносятся. Отсутствующие файлы не создаются и не удаляются из БД.

Применение (backend остановлен):
go run ./cmd/migrate-files -db test.db -root uploads -apply -report ../file-migration-result.json

Перед изменением схемы команда автоматически делает согласованную резервную
копию SQLite: test.db.before-file-migration-ДАТА.bak через VACUUM INTO.
Затем копирует файлы, проверяет SHA-256, обновляет ссылки в БД.
Оригиналы остаются на месте. Миграция учитывает также мягко удалённые записи.
Повторный запуск не создаёт дубликаты: already_migrated, проверка SHA-256.
При missing/error код завершения 1; остальные доступные записи могут быть
успешно перенесены — смотрите построчный отчёт. Исправьте причину и повторите.
Старые почтовые вложения попадают в mail/legacy: направление не угадывается.
Карточка компании переносится, если uploads/company_card.pdf существует.
Импорт Excel не сохраняет исходный файл постоянно и не участвует в переносе.

На Linux собрать команду в каталоге исходников backend:
go build -o migrate-files ./cmd/migrate-files
Положить исполняемый файл в доступное пользователю brm место, затем:
sudo systemctl stop brm
sudo -u brm /путь/migrate-files -db /var/lib/brm/test.db -root /var/lib/brm/uploads -report /var/lib/brm/file-migration-preview.json
После проверки отчёта:
sudo -u brm /путь/migrate-files -db /var/lib/brm/test.db -root /var/lib/brm/uploads -apply -report /var/lib/brm/file-migration-result.json
sudo systemctl start brm
Проверить открытие старого документа и загрузку нового через сайт.

3. Резервное копирование и откат
Сохранять БД и весь каталог uploads одной согласованной резервной копией.
Имена папок читаемы и в физической копии. Не переименовывать файлы вручную:
ключи в БД должны соответствовать диску.
Для отката миграции остановить backend и восстановить БД из созданного .bak
штатным SQLite backup/restore. Старые исходные файлы не удалены. Новые копии
можно пока оставить. Не откатывать старую БД после появления новых рабочих
данных без отдельного плана: такие данные потеряются.
Не удалять SQLite -wal/-shm при работающем backend.

На этом этапе автоматическая отправка в Облако Mail.ru не добавляется.
Перенос и публикация на рабочем сервере — отдельная операция.
